= 处理单元
:description: 八路再锁存、源码里的意图注释，以及尚未实现的交叉模块。
:navtitle: 处理单元

`EventRegister/st_processing_unit.v` 接在多槽存储后面。测试台 `tb_processing` 的接法是：环振驱动 `st_flash_to_bram`，八路 `reqs_out` 作为处理单元的 `ens`，256 位 `datas_out` 作为 `datas_in`。

== 源码里的注释

模块头上的注释写的是这条工作方向，不是已实现的算法：

[quote]
现今指令集到操作系统的操作本质上是把固定或者有限组合的结果复现出来，不是针对最终意图。就如 sorry、sry、抱歉、对不起，甚至一个表情，可以代表一个意图。

注释把“同一意图的不同表面形式”当成处理单元要面对的问题。当前电路还没有比较这些形式。注释下面实例化的 `st_cross_a` 模块体是空的。

== 八路再锁存

处理单元里有八只 `st_32_2ske_latch`，各自吃 `datas_in` 的 32 位和 `ens` 的一位。写使能是 `ens[i] & ~reqs_out[i]`：这一路的请求一旦置位，使能就被自己关掉，避免同一笔数据把槽重写一遍。

八路 `ack` 被接成常数 0。按 xref:handshake.adoc[请求锁存] 的规则，请求置位之后不会被应答清除。`req_out` 是八个 `req` 相与，也就是八路都锁住时才为高。

`reset` 仍会清除数据和请求。

== 交叉模块

`st_cross_a` 的端口已经定下来：

[cols="1,2",options="header"]
|===
|端口 |处理单元里的接法

|`data_in`
|第 0 路锁存的 32 位输出，不是八路一起。

|`en`
|第 0 路的 `req`。

|`states_in`
|常数 `32'h00004000`。源码没有解释这一位。

|`formula`
|常数 `32'h00000000`。

|`converge_out`、`pending_out`、`diverge_out`
|各 8 位。模块体为空，没有驱动。

|`reset`
|与处理单元的复位相连。
|===

空模块不会把收敛、悬挂或发散算出来。第 1 到第 7 路锁存的数据目前也没有送进 `st_cross_a`。

== 和存储测试的差别

`tb_processing` 与 `tb_test_ring` 使用同一份 `STORAGE/flash_memo.hex`，地址都来自 `st_flash_to_bram` 内部的步进器。处理单元测试多接了一级 `st_processing_unit`，并用 `unit_req` 观察八路是否都已锁住。两个测试台都会在中途把存储侧的 `ack` 拉高一个时间单位再放开，用来清存储槽的请求。处理单元内部的 `ack` 仍然是 0，不受这个测试台信号影响。
